# Chess Engine v7.1.1 → v7.2–v7.4 Optimization Plan

## Objective

Upgrade the existing `v7.1.1_mix` chess engine for maximum playing strength and efficiency under these constraints:

- **CPU only**
- **Exactly one search thread / one CPU core**
- **No GPU**
- Preserve the existing classical alpha-beta/PVS search framework unless testing demonstrates that a change is necessary.
- Prioritize **Elo per unit of CPU time**, not merely raw nodes per second.
- Preserve correctness at every stage.

The engine is currently best classified as a **classical search + classical evaluation + small NNUE residual/blend hybrid**.

The most important optimization target is the NNUE evaluation path. The current implementation reconstructs NNUE input/evaluation work repeatedly instead of maintaining an incremental accumulator. This should be fixed before making the network substantially larger.

---

# 1. Current Architecture

The engine currently contains:

- Bitboard representation
- Classical evaluation
- PVS / alpha-beta search
- Iterative deepening
- Transposition table
- Null-move pruning
- Late Move Reductions (LMR)
- Aspiration windows
- SEE
- Killer/history/counter-move style ordering
- NNUE evaluation
- Classical + NNUE blended evaluation
- Single-core CPU operation

The NNUE network is approximately:

```text
768 → 160 → 32 → 1
```

The feature space is approximately:

```text
12 piece types × 64 squares = 768 features
```

The network uses ReLU-style activations.

The current blend is conceptually:

```text
classical = C
nnue      = N
delta     = N - C

delta = clamp(delta, -400, +400)

final = C + delta / 2
```

Therefore:

```text
final = C + 0.5 * clamp(N - C, -400, +400)
```

This fixed 50% blend must become tunable.

---

# 2. Critical Design Principle

Do NOT immediately increase NNUE network size.

The current network is small enough to be useful on one CPU core, but the evaluation path is not sufficiently optimized.

The priority is:

```text
incremental NNUE
        ↓
remove repeated allocations/reconstruction
        ↓
integer/quantized inference
        ↓
residual training
        ↓
lazy evaluation
        ↓
TT static evaluation
        ↓
search tuning
        ↓
only then consider a larger network
```

A small, efficiently incrementally updated NNUE can outperform a larger network that is repeatedly evaluated from scratch.

---

# 3. Phase 1 — Implement an Incremental NNUE Accumulator

## Priority: CRITICAL

Replace the current approach where every NNUE evaluation reconstructs the feature set and sums all active feature weights.

The NNUE first layer should maintain an accumulator:

```python
acc[160]
```

or an equivalent structure.

The accumulator represents:

```text
first_layer_bias
+
sum(first_layer_weight[active_feature])
```

for the current position.

## Initial accumulator construction

For a fresh position:

```python
acc[:] = bias1

for every piece on the board:
    idx = feature(piece, square, side_to_move)
    acc += W1[idx]
```

This initialization may remain relatively expensive because it happens only when starting/rebuilding a position.

## Move updates

For a normal quiet move:

```text
remove moving piece from source square
add moving piece to destination square
```

Therefore:

```python
acc -= W1[feature(piece, from_square)]
acc += W1[feature(piece, to_square)]
```

For a capture:

```python
acc -= W1[feature(moving_piece, from_square)]
acc += W1[feature(moving_piece, to_square)]
acc -= W1[feature(captured_piece, capture_square)]
```

For an en-passant capture:

```text
remove moving piece from source
add moving piece to destination
remove captured pawn from its actual board square
```

For promotion:

```text
remove pawn feature at source
add promoted-piece feature at destination
```

Handle the exact feature convention consistently.

## Side-to-move handling

The feature transformation must exactly match the current training/inference convention.

If the feature index depends on side to move, changing side to move can invalidate the accumulator.

Preferred implementation:

- Either maintain separate accumulators for both perspectives/side-to-move states.
- Or use a feature representation that allows the accumulator to be updated efficiently when the side to move changes.
- Do NOT simply flip the board and rebuild the accumulator at every node.

The implementation must be designed around the actual feature indexing used by the existing network.

# 4. Accumulator Stack

The search already operates by ply.

Add an accumulator state associated with each ply:

```python
nnue_acc_stack[ply]
```

A simple first implementation is acceptable:

```python
child_acc = parent_acc.copy()
apply_move_deltas(child_acc, move)
```

Because the accumulator has only around 160 elements, this is still vastly cheaper than reconstructing it from all pieces.

Later, optimize further if profiling shows the copy is significant.

A more advanced implementation can store reversible deltas rather than copying the full 160-element vector.

Do NOT optimize this prematurely.

Correctness comes first.

---

# 5. NNUE Make/Unmake API

Create a clean interface similar to:

```python
nnue_make_move(parent_acc, move, position, child_acc)
```

and/or:

```python
nnue_update_accumulator(parent_acc, move, position, child_acc)
```

The accumulator update must support:

- Quiet moves
- Captures
- Promotions
- En-passant
- Castling
- Null moves if the search uses them

Castling requires moving both king and rook.

For every move type, verify that:

```text
incremental accumulator
==
freshly rebuilt accumulator
```

after the move.

This equality test is mandatory.

---

# 6. Build a Reference NNUE Path

Before replacing the current implementation, retain a slow reference implementation for testing.

Create two evaluation paths:

```text
NNUE_REFERENCE
NNUE_INCREMENTAL
```

For thousands of random legal positions and random legal move sequences:

```text
reference accumulator
==
incremental accumulator
```

and:

```text
reference NNUE output
==
incremental NNUE output
```

within exactly zero difference for integer arithmetic, or within a documented tolerance if floating-point arithmetic is temporarily retained.

Do not proceed to optimization until this test passes reliably.

---

# 7. Remove Per-Evaluation NNUE Allocations

The current evaluation path creates temporary arrays/buffers such as:

```python
np.empty(...)
```

inside hot evaluation functions.

Eliminate this where possible.

The goal is:

```text
make move
    ↓
update accumulator
    ↓
NNUE forward pass
```

rather than:

```text
evaluate
    ↓
allocate buffer
    ↓
scan board
    ↓
construct feature list
    ↓
sum weights
    ↓
forward pass
    ↓
discard buffers
```

This should significantly reduce memory traffic and allocation overhead.

---

# 8. Phase 2 — Quantize NNUE

## Priority: HIGH

After incremental evaluation is correct, convert the NNUE toward integer/fixed-point inference.

The exact quantization scheme must be determined from the actual trained weight ranges.

Do NOT blindly cast float32 weights to integers.

The intended structure is approximately:

```text
feature weights → int8/int16
first accumulator → int32
hidden weights → int8/int16
biases → integer
output → integer
```

A possible structure is:

```text
W1     int16
bias1  int32
acc    int32

W2     int8/int16
bias2  int32

W3     int16
bias3  int32
```

The exact types should be selected using profiling and numerical validation.

## Quantization requirements

Measure:

- maximum absolute weight
- minimum/maximum bias
- activation range
- output range
- saturation frequency

Avoid overflow.

The quantized network should be compared against the float reference on a large set of positions.

Record:

```text
mean absolute error
maximum error
correlation
sign agreement
evaluation distribution
```

The quantized network is acceptable only if its playing strength is not materially worse.

---

# 9. SIMD-Friendly Layout

Store NNUE weights in a layout that is friendly to contiguous memory access.

For the first layer, feature updates should look like:

```python
acc += W1[feature]
```

where:

```text
W1[feature]
```

is a contiguous 160-element vector.

Prefer compact arrays with predictable strides.

Avoid Python object arrays.

Avoid nested Python lists in the hot inference path.

Use Numba-compatible numeric arrays if the engine is using Numba.

The final implementation should compile to efficient native loops.

---

# 10. Phase 3 — Convert NNUE Into a Residual Predictor

## Priority: HIGH

The current architecture computes:

```text
NNUE absolute evaluation - classical evaluation
```

and then blends that difference.

A better design for this engine is to train the network explicitly to predict the **residual**.

Define:

```text
C = classical evaluation
T = training target
R = T - C
```

Train the network to predict:

```text
R
```

instead of directly predicting:

```text
T
```

The engine then becomes:

```text
final = C + residual
```

Optionally:

```text
residual = clamp(residual, -CLIP, +CLIP)
final = C + weight * residual
```

This makes the network's purpose explicit:

```text
classical evaluation
+
neural correction
```

---

# 11. Residual Target Clipping

Initially train against:

```text
R = clamp(T - C, -400, +400)
```

if the engine's current blend uses a ±400 centipawn correction limit.

Test alternatives:

```text
±300
±400
±500
±600
```

Do not assume ±400 is optimal.

The clip should be treated as a tunable engine parameter.

---

# 12. Make NNUE Blend Parameters Configurable

Do not hard-code:

```python
delta // 2
```

Create parameters such as:

```python
NNUE_WEIGHT
NNUE_CLIP
```

with:

```python
final = classical + NNUE_WEIGHT * clamp(nnue_residual, -NNUE_CLIP, +NNUE_CLIP)
```

For integer implementation:

```python
final = classical + (residual * weight) // scale
```

For example:

```text
weight = 25%
weight = 37.5%
weight = 50%
weight = 62.5%
weight = 75%
weight = 100%
```

Test all of these through self-play.

Do not select the strongest-looking value from a handful of games. Use statistically meaningful matches.

---

# 13. Optional Phase-Dependent NNUE Weight

Once the fixed-weight blend is working, test a phase-dependent blend.

Conceptually:

```text
final = C + w(phase) * residual
```

where `phase` is based on material/game phase.

The reason is that the classical evaluator contains explicit endgame logic, while the NNUE may be more useful in complex middlegame positions.

Initial experimental values could be around:

```text
opening/middlegame: 0.60–0.70
late middlegame:    0.55–0.65
endgame:            0.35–0.50
```

These are starting points only.

The final values must be learned through self-play.

Do not assume that stronger NNUE weight is always better.

---

# 14. Phase 4 — Lazy NNUE Evaluation

## Priority: MEDIUM/HIGH

Avoid evaluating the NNUE when the cheap classical evaluation is already sufficient.

Evaluation order should become:

```text
cheap classical evaluation
        ↓
can search/pruning decision be made?
        ↓
yes → use cheap evaluation
        ↓
no
        ↓
full classical evaluation if required
        ↓
NNUE residual
```

The goal is to avoid paying neural inference cost at every node.

At non-PV nodes, where the score only needs to establish a bound, exploit the cheap evaluation aggressively but safely.

Examples of situations to investigate:

```text
static_eval - margin >= beta
```

or:

```text
static_eval + margin < alpha
```

Only introduce a lazy shortcut when it has been validated against the full evaluator.

False pruning is unacceptable.

---

# 15. Split Classical Evaluation Into Cheap and Expensive Components

The current classical evaluator performs many operations.

Separate it into:

## Cheap evaluation

Include things such as:

- Material
- Basic PST
- Tempo
- Very cheap pawn terms
- Other O(1)/very-low-cost terms

## Expensive evaluation

Potentially include:

- Detailed king attack analysis
- Pins
- Rook structure analysis
- Pawn threats
- King shield calculations
- Complex endgame geometry
- Other repeated bitboard scans

The intended evaluation pipeline becomes:

```text
cheap HCE
   ↓
obvious bound?
   ↓
return
   ↓
full HCE
   ↓
NNUE residual
```

Benchmark every stage.

Do not split an evaluator merely for conceptual cleanliness; retain a split only if it improves actual search performance/Elo.

---

# 16. Phase 5 — Store Static Evaluation in the TT

## Priority: MEDIUM

The transposition table currently stores core search information such as:

```text
key
move
depth
flag
score
generation
```

Investigate adding:

```text
static_eval
```

to the TT entry.

Conceptually:

```text
TT entry:
    key
    best_move
    depth
    score
    static_eval
    bound_flag
    generation
```

Then:

```python
if TT entry has valid static_eval:
    use it
else:
    calculate static_eval
```

This can reduce repeated evaluation work.

The TT layout must remain compact enough that the increased entry size does not destroy cache efficiency.

Benchmark multiple layouts.

It is possible that a larger TT entry performs worse because of increased cache misses.

# 17. Phase 6 — Search Tuning

Do NOT rewrite the search before optimizing evaluation.

The current search already contains sophisticated mechanisms:

- PVS
- Alpha-beta
- TT
- Null move
- LMR
- Aspiration windows
- SEE
- Killer moves
- History
- Counter moves
- Capture history
- Razoring
- Futility/reverse futility
- Extensions

The first goal is to make the current search consume more useful nodes.

# 18. LMR Tuning

Current LMR is approximately based on:

```python
reduction = function(depth, move_number)
```

with a logarithmic formula.

After NNUE optimization, test several reduction strengths.

Candidate denominators:

```text
2.0
2.25
2.5
2.75
3.0
```

Candidate base offsets:

```text
0.50
0.75
1.00
1.25
```

Do not optimize only for nodes/sec.

A stronger reduction may increase NPS while reducing Elo.

Primary metric:

```text
Elo
```

Secondary metrics:

```text
NPS
nodes searched
fail-high rate
fail-low rate
re-search rate
TT hit rate
```

---

# 19. Null-Move Tuning

Current null-move reduction is approximately:

```text
2 + depth / 4
```

Test nearby schedules such as:

```text
2 + depth/5
2 + depth/4
3 + depth/4
3 + depth/3
```

Check tactical test suites for zugzwang/endgame failures.

Do not increase null-move aggressiveness solely because it makes the engine faster.

---

# 20. Aspiration Window Tuning

Measure:

- aspiration fail-high frequency
- aspiration fail-low frequency
- number of re-searches
- average extra nodes caused by failed windows

Test several initial window sizes.

Keep the window wide enough to avoid excessive re-searching while retaining the benefit of narrow alpha-beta windows.

# 27. Do Not Make These Changes Yet

Do NOT initially:

- Increase NNUE from 160 hidden units to 256+
- Add a large residual CNN/ResNet
- Add GPU inference
- Rewrite the entire search
- Add many new pruning heuristics
- Add multicore search
- Replace the bitboard representation
- Add complex neural architectures

The current objective is one-core CPU strength.

The most likely large gain is from **evaluation efficiency**, not architectural complexity.

# 29. Target Performance Characteristics

The optimized engine should aim for:

1. **No full NNUE feature reconstruction during normal search.**
2. **No unnecessary heap allocation in the NNUE hot path.**
3. **Incremental accumulator updates on make-move.**
4. **Integer/quantized NNUE inference where accuracy permits.**
5. **NNUE trained specifically as a correction to the classical evaluator.**
6. **Configurable NNUE weight and clipping.**
7. **Lazy neural evaluation where safe.**
8. **Optional cached static evaluations in the TT.**
9. **Search heuristics tuned empirically rather than by intuition.**
10. **One-core CPU optimization as the primary target.**


If a change reduces NPS but increases Elo, keep it if the improvement is statistically meaningful.

If a change increases NPS but reduces Elo, revert it unless it is necessary for a later improvement.

# 31. Definition of Success

The project is successful when the final engine demonstrates a measurable improvement over `v7.1.1_mix` under:

```text
1 CPU core
no GPU
same time control
same hash size
same opening suite
same hardware
```

The primary metric is:

```text
playing strength / Elo
```

with:

```text
NPS
evaluation cost
NNUE calls/node
TT efficiency
```

used as supporting diagnostics.

The ultimate objective is not merely a faster engine.

It is:

> **Maximum chess strength per single CPU core without GPU acceleration.**
